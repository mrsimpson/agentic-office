4. Bring in an agent

An agent is a participant like you. It follows the meeting and acts through tools: it can keep the minutes, record decisions, raise its hand, write documents, show slides and speak. Several agents can take part in the same meeting, for example Claude Code, opencode and Kiro next to each other. The agent runner (office agent run) keeps each one in the meeting, so that people can talk to it in plain words. Each agent needs:

  • its own participant ID and key, so that everyone sees who said or recorded what;
  • its own folder, where its tool keeps its work and settings;
  • the hub and its certificate, as for a human (see Set up once). On the computer of a human participant, the agent uses the same hub profile.

Start the agent with the runner

Section titled “Start the agent with the runner”

Claude Code, opencode and Kiro work in turns: they answer and then wait for you. In a meeting nobody types into their chat, so they would stop listening. The agent runner keeps them in the meeting. Start one runner per agent:

The program after -- is the harness: the program that runs the agent. The runner talks to it over the Agent Client Protocol (ACP). The runner:

  1. joins the meeting with the agent’s key (OFFICE_KEY) and follows the local log;
  2. starts the harness and hands it the office tools for this meeting. You do not add the office as an MCP server in the harness;
  3. tells the agent its role and how the meeting works;
  4. decides when to wake the agent: at each change of speaker, or after each sentence of someone else with a model that you bring (see When the runner wakes the agent). When it wakes the agent, it sends everything the others said since the last time: who spoke, whether a human or an agent, and what they said;
  5. at the end of the meeting, gives the agent time for its last work, for example the minutes. Then it stops. Stop it earlier with Ctrl+C.

The agent decides by itself whether someone addressed it. So people talk to it in plain words, without a keyword: “Claude, what did we decide on the budget?” or “Can the minute taker read back the last point?”. The agent does not interrupt a speaker: it answers when the speaker has finished, raises its hand, or writes. It speaks only through the tool utterance_say; what it writes in its own chat reaches nobody. If an agent ends its turn with text in its chat and does not speak, the runner logs a warning with the text (WARNING: the agent wrote a reply in its chat but did not speak it) and asks the agent once whether the text was meant for the meeting. If the agent again does not speak, the runner logs that the reply reached nobody.

Start each agent in its own folder and terminal, with its own key. Log in to each harness once before, as you would to use it alone. The runner does not log in for you.

The runner prints what it does on its terminal, each line starting with office agent:: the session, the wake strategy, each wake-up, each tool call, each permission decision, each decision of a model with its reason or its probabilities, and what the agent wrote in its chat.

When the runner stops. After the meeting ended, it sends a last prompt, lets the agent finish its work and stops. It also stops when the agent itself leaves the meeting, on Ctrl+C or SIGTERM, and when the harness stops by itself, which is an error (exit code 1). It then stops the harness: it closes its input, then sends SIGTERM and at last SIGKILL to its process group.

What the agent may do. The harness asks the runner before it uses a tool. By default the runner allows the office tools and rejects everything else, for example shell commands or edits of files. To allow more, give patterns of tool titles with --allow (* is any text). The patterns replace the default, so include the office tools, for example --allow '*office*' --allow 'read*'. --allow '*' allows everything. A harness that does not ask, because its own settings allow a tool, follows its own settings.

More exactly, the runner offers the harness no file system and no terminal of its own. By default it allows the call of an office tool, such as mcp__office__utterance_say, unless its kind is execute, edit, delete or move, and rejects every other call. With --allow it allows exactly the calls whose title matches one of the patterns; case does not matter. Configure the harness itself for what it may do without asking.

--cwd DIR sets the folder of the agent’s session; the default is the current folder.

Give each agent a role

Section titled “Give each agent a role”

The role tells the agent what to do in the meeting. Write it in plain words, with --role TEXT or in a file with --role-file FILE. Give each agent its own role, so that they do not talk over each other. For example:

  • minutes.md, for Claude Code:

    You are Claude, the minute taker. Keep the minutes with minutes_update after each topic. Answer when someone asks you about what was said or decided. Otherwise stay silent.

  • tasks.md, for opencode:

    You are opencode, the task keeper. When someone takes on a piece of work, create a task with task_create, with the person as the assignee. Speak only when someone asks you about tasks.

  • decisions.md, for Kiro:

    You are Kiro, the decision keeper. Record each decision with decision_record, in one clear sentence. Speak only when someone asks you about decisions.

All three can run in the meeting weekly at the same time. Each agent hears the others: the runner also tells it what the other agents said, and that they are agents.

When the runner wakes the agent

Section titled “When the runner wakes the agent”

Waking a harness with a large model costs time and money. So you choose when the runner wakes the agent, with --wake:

--wake The runner wakes the agent You need
turn-end (the default) at each change of speaker: when someone else ends their turn nothing
llm when a forwarding judge says so, after each sentence of someone else a general language model, for example a small one in Ollama, or your own program
decision-model when a decision model says so, after each sentence of someone else a key for a decision model, for example TypeSafe Jev or Cloudflare Clef

The office ships no model; you bring it. A forwarding judge is the model or program to which the runner forwards its question, for example a general language model; it answers with yes or no and a reason. A decision model is a small model made for such questions; it answers with probabilities.

With turn-end, the runner says at start that it does not notice a new topic within a monologue.

With llm or decision-model, the runner asks the model after each sentence of someone else. It wakes the agent when the model says that:

  • someone addressed the agent, by name, by its role or by the context;
  • what was said concerns the agent’s role, so it should contribute now. This also works in the middle of a long monologue, for example when the speaker moves to a new topic;
  • a topic or a block of topics has ended. Then the runner also gives the agent the task for the end of a topic. Set it with --topic-task, for example --topic-task "Update the minutes and record the decisions of this block.".

What did not wake the agent stays and reaches it with the next wake-up, so it misses nothing.

When the model fails, the runner falls back to turn-end. A failure is an error, no answer within --decide-timeout (default 10s), or an answer the runner cannot read.

  • After one failure, the runner does not wake the agent. The sentences wait until the speaker ends the turn.
  • After three failures within five minutes, the runner works as with turn-end and says so once on its terminal. It then wakes the agent at each change of speaker, and asks the model again once after each change of speaker, at the next sentence. When the model answers again, the runner switches back and says so.

When you speak, the ears end your turn after a short silence: 1.8 seconds by default. Change it with office meeting join --turn-silence 2.5s. Text that you type with office say does not end your turn: run office signal turn-end when you are done.

What the agent receives

Section titled “What the agent receives”

When the runner wakes the agent, it sends everything that others said since the last time, oldest first, one sentence per line: the event ID, the name, whether the speaker is a human or an agent, and the text. Then it says whose turn has ended, or that the speaker may still be speaking, so the agent should raise its hand or write instead of interrupting. For example:

  • The agent never gets its own sentences, its own end of turn, or sentences that are off the record. A sentence that went off the record before it was sent is never sent. If it was sent already, the runner wakes the agent as soon as it is free, names the event and says that it is off the record.
  • One prompt runs at a time. While the agent works, what comes waits and goes out together in one prompt when the agent ends its turn. An end of turn without new sentences wakes nobody.
  • With a model, the prompt also says whom the speaker addressed and, when a block of topics has ended, gives the task for that (--topic-task; the default is to update the minutes and record the decisions and tasks of the block, if the role asks for it).
  • After the meeting ended, the last prompt carries what is left and asks the agent to finish the work of its role, for example the minutes, decisions or tasks, without speaking: the ended session takes no new sentences.

Bring a decision model

Section titled “Bring a decision model”

A decision model answers questions about the meeting with probabilities. The runner speaks its API, the System One API, with --wake decision-model. Give the full URL of the endpoint with --decide-url; the runner appends nothing. Give the model with --decide-model and the key in OFFICE_DECIDE_KEY. The runner sends the key as a bearer token and never logs it.

TypeSafe Jev. The endpoint is https://api.typesafe.ai/v1/systemone; the models are jev-latest and jev-1.14.0. Input costs $0.042 per million tokens; output is free.

Cloudflare Clef (Workers AI). Cloudflare states that Clef is compatible with the Jev API. The endpoint has your account ID in it; the models are clef and clef-flash. Input to Clef costs $0.24 per million tokens.

OpenRouter lists Jev too, but its chat endpoint does not take the parameters that --wake llm needs. Use the System One endpoint with --wake decision-model instead.

The runner asks three questions: should the agent act now, has a topic ended, and whom did the speaker address (a participant or nobody). A probability at or above --decide-threshold (default 0.5) counts as yes. Raise it if the agent wakes too often; lower it if it misses questions. The runner prints the probabilities on its terminal, for example act 0.93, topic_closed 0.10, addressed kiro-bot (0.80).

Bring a forwarding judge

Section titled “Bring a forwarding judge”

The runner forwards a short request about the meeting to the forwarding judge, which answers with JSON. Use --wake llm and connect it in one of two ways.

A server with an OpenAI-compatible API. It must support structured output with a JSON schema (response_format of type json_schema). Give the base URL that ends in /v1 with --decide-url and the model name with --decide-model. The runner posts to <URL>/chat/completions.

The models are examples. Any model works that the server can run with structured output; try a small one first. If the server needs a key, put it into OFFICE_DECIDE_KEY. The runner sends it as a bearer token and never logs it.

Your own program. Give a shell command with --decide-cmd, for example --wake llm --decide-cmd "python3 decide.py". The runner starts it once per check. It writes a request as JSON to the program’s standard input:

new are the sentences the agent has not got yet; the last one was just said. context are up to 20 earlier sentences. turn_ended says whether the speaker has ended their turn. The program writes the answer as JSON to its standard output:

act (wake the agent now) and topic_closed (a topic has ended) must be there. addressed and reason may be empty. With a server, the runner sends the same request as the user message of a chat completion, with temperature 0 and a strict JSON schema for the answer.

How often the runner asks. With llm or decision-model, the runner asks after each sentence of another participant, and once more when that participant ends the turn. One check runs at a time: sentences that come meanwhile wait, and the next check gets all of them. A check also runs while the agent works; a wake-up then waits until the agent is free. The runner wakes the agent when the answer says that the agent should act, or that a topic has closed.

Where the model runs matters. A forwarding judge or a decision model gets the text of the meeting, as the agent’s own model does. A hosted model sends this text to its provider. A local model keeps it on your computer. Sentences off the record are never sent.

Start an agent with a configuration file

Section titled “Start an agent with a configuration file”

The commands above are long. Put the options into a file instead, and start the agent with office agent run alone. The file is YAML. There are two places for it:

  • your user file, config.yaml in your configuration folder, next to your key: ~/.config/agentic-office/client/config.yaml on Linux, ~/Library/Application Support/agentic-office/client/config.yaml on a Mac. Use it for what holds for all your projects, for example your decision model;
  • the project file, .office/config.yaml in the folder where you start the command. Use it for what belongs to the project, for example the role of the agent.

The project file wins over the user file, key by key. Environment variables win over both files, and the options on the command line win over everything. So you can still change one thing for one start, for example office agent run --wake turn-end.

Keep one folder per role in the project, each with its own .office/config.yaml, and check the files in with the project. For example, agents/minutes/.office/config.yaml:

Then:

Keys never go into a file. The file only names the environment variable that holds the key (key-env). So nobody finds a key in the repository. If two models need two keys, give them two variables, for example key-env: TYPESAFE_KEY in one file and key-env: CLOUDFLARE_KEY in the other.

A typo stops the command and names the file, the line and the key, for example line 6: unknown key agent.wake.modell. To see what the runner will use and where each value comes from, run office config show in the same folder. It shows whether the key variable is set, but never the key. office help config lists all keys.

Relative paths in the project file, such as role-file, are relative to the folder where you start the command. A flag that changes the wake strategy, for example --wake turn-end, leaves out the wake settings of the files that do not fit it. Keys that exclude each other are role and role-file, and wake.command and wake.url: when a higher source sets one, the other one from a lower source no longer counts.

Without the runner: the tools only

Section titled “Without the runner: the tools only”

A harness can also use the office directly as an MCP server, without the runner. Then the agent must keep reading new events itself, and it stops listening when its turn ends. This suits short jobs, for example writing the minutes after a meeting. office mcp is a local MCP server on standard input and output. It takes the same flags and OFFICE_* variables as the CLI, and --session sets the default session of the tools. The key must exist and be registered first. Add office mcp as an MCP server in the agent’s folder. In a configuration file, write absolute paths: no ~ and no $HOME. The cat <<EOF in the Kiro example fills them in for you.

Session tools take an optional session; the default is --session, OFFICE_SESSION, or the only session this participant joined from this machine. Each tool returns one JSON object, as text and as structured content, in the same shape as the --json output of the CLI (see below). Errors set isError and return {"error":{"code","message"}}. Not offered are the key and admin commands (set up the key with the CLI), the gateway view and the ears (an agent has no microphone), and a tool that waits for new events: the agent reads the log file.

The log. meeting_join returns logPath. The replicator runs inside the MCP process, so the replication lives as long as that process: it stops when the client closes the connection, when the process ends, when you leave, and after the meeting ended. Call meeting_join again to restart it. If office meeting join already runs a replicator for the same participant, meeting_join reuses it. Read results in scripts: --json

Section titled “Read results in scripts: --json”

With --json (or OFFICE_JSON=1), a command prints exactly one JSON object on one line on standard output, also when it fails, so a script can pipe it to jq. The field names are camelCase. An event has the same form as its line in the local log. On failure the object is {"error": {"code": "permission_denied", "message": "…"}}: the code is the code of the hub or one of usage, no_key, no_session and error. The exit code is 0 for success, 1 for an error and 2 for a wrong call. office help json has the details, and the help of each command names its result.
