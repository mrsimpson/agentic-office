2. Run a hub

The operator does this once per team. The hub must be reachable by all participants on one port, by default 8740. Below, hub.example.org stands for the name of your server.

Run the hub as a binary (on Linux or macOS) or as a container with Docker or Podman. On a Mac, use the binary. It runs directly on macOS, without a virtual machine. Apple’s container is not a good base for a hub yet: in our tests its service stopped answering, and container exec and container system stop hung (see Troubleshooting).

The first system admin

Section titled “The first system admin”

The hub has two kinds of admins. A system admin runs the hub: creates tenants and users and names other system admins. A tenant admin runs one tenant: adds and removes its members. A tenant is one organisation with its own repository; its sessions and records are visible only to its members.

A system admin is never a member of a tenant, and a member is never made a system admin. If you run the hub and also work in a tenant, use two users with two different keys.

You are the first system admin. Give this user a name that tells it apart from the users who work in a tenant, for example root, and create its key on your own computer first:

Start the hub with the binary

Section titled “Start the hub with the binary”

On the server. CFG is where the programs keep their files: $XDG_CONFIG_HOME/agentic-office if you set that variable, else ~/.config/agentic-office on Linux and ~/Library/Application Support/agentic-office on macOS. The first line sets it for all three:

  • The data of the hub lives in $CFG/hub (-data-dir changes it): the users and keys, the TLS certificate and the archive with all sessions and records.

  • On the first start, the hub creates a self-signed TLS certificate for the names in -tls-hosts, in tls.crt. A start that fails writes nothing, so you can fix the flags and start again. If a later start names a host in -tls-hosts that the certificate misses, the hub does not start: delete tls.crt and tls.key to get a new certificate, and send the new fingerprint to the participants. To use your own certificate, see Use your own certificate.

  • office-hub -h lists every flag with its default and says what the hub keeps in its data directory: the certificate, the hub repository with the users, tenants and memberships, and one Git repository for each tenant. The hub needs the git command line tool.

  • Participants can push changes to the artifacts with Git (see Work on files in a local directory). Three options set the size limits of a push. A push over a limit is refused:

    Option Default Limit
    -git-max-push-mib 32 Size of one push, in MiB
    -git-max-file-kib 1024 Size of one file, in KiB
    -git-max-files 500 Number of files that one push changes

  • The hub needs the git command line tool in its PATH. Git runs a hook program to check every push. This program is the hub binary itself: at start, the hub writes a small script that calls the binary at its real path. Do not move or delete the binary while the hub runs, and restart the hub after you replace it.

  • -first-system-admin names the first system admin at the first start. The hub ignores it later. A system admin is never a member of a tenant: if you also work in a tenant, use a second user with another key.

  • To keep the hub running, start it as a service of your system, for example with systemd or launchd.

Or start the hub as a container

Section titled “Or start the hub as a container”

With Docker or Podman (podman instead of docker):

The last command copies the certificate; the participants usually do not need the file (see below). --restart unless-stopped starts the hub again after a restart of the server. When you pass flags to the image, pass all of them, as in the example (the default command is -data-dir /data -addr 0.0.0.0:8740 -signing-key /data/signing.key).

Health check. For a container platform (Kubernetes, a load balancer), the hub answers GET /healthz with 200 and ok on its TLS port. It needs no login and reads no data. The platform has to accept the self-signed certificate: the Kubernetes probe httpGet with scheme: HTTPS does.

The signing key

Section titled “The signing key”

The hub signs the tree heads of the meeting logs. A tree head is a short proof that a log has not changed. You give the hub the signing key at every start with -signing-key FILE. The hub never creates a signing key by itself, and it does not start without the flag, or if the file is missing, broken or readable by others.

  • office-hub keygen FILE creates the file once. It writes the private key with mode 0600, prints the public key and refuses to overwrite an existing file.
  • The hub logs the public key at start: signing key of tree heads ….
  • Keep the file with your other secrets and back it up. Start the hub with the same file every time. If you replace it, tree heads that were signed with the old key no longer verify.
  • How clients pin the public key of the hub is still open (issue #41).

Use your own certificate

Section titled “Use your own certificate”

With a certificate from your own authority or from Let’s Encrypt, clients need no stored certificate. Start the hub with the files and its public address:

  • The certificate file is PEM and may hold the whole chain. The key file is PEM (PKCS #8, PKCS #1 or SEC 1). Or put both into the data directory as tls.crt and tls.key: the hub never overwrites existing files.
  • Participants then trust the system roots: they use office hub add without a stored certificate (see Set up once), or give no certificate file.
  • -public-url is the address in stage links. It defaults to https://<listen address>.
  • The hub reads the certificate at start. Restart it after you renew the certificate.

The self-signed certificate of the hub is valid for 820 days, because macOS and the browsers on it reject server certificates that are valid for more than 825 days. The hub warns at start when its certificate is valid for longer. Delete tls.crt and tls.key and restart to get a new one. A client with a certificate file trusts only the certificates in that file, not the system roots.

When the hub restarts

Section titled “When the hub restarts”

Stop the hub with SIGINT or SIGTERM (Ctrl+C, systemctl stop, docker stop). It then writes every changed session to the archive once more. The hub writes the sessions that changed every 30 seconds while they run (-archive-interval), and at once when a session ends.

  • After a clean stop the hub starts again without a wait. Sessions that have not ended are back with all their events.
  • After a crash the events after the last write are lost on the hub, but the participants have them, and their clients fill them in by themselves. Until a participant has done so, for at most -restore-wait (10 seconds), commands of a session that has not ended fail with unavailable. Repeat the command; nothing is lost or stored twice.
  • Users, keys, tenants and memberships are files in the hub repository and survive. Access tokens do not: clients sign in again.
  • Releases survive too (see Release what a session created): a session whose grace period ended while the hub was down is released at start, and a release that the stop cut off is completed, once.
  • A known gap (issue #47): a session that the hub never wrote to the archive is unknown after a crash until a participant offers a whole copy of its log.

Call the hub directly

Section titled “Call the hub directly”

Every interface of the hub is a Protobuf contract served with Connect RPC, which is plain HTTP with JSON. You can call any command with curl, for example to test the hub from a script:

  • Every call carries an access token (Authorization: Bearer), except GetChallenge and ExchangeChallenge, which give you one: sign the challenge with your key. A token lives 15 minutes (-token-ttl). The Go package hub/identity/api/auth does this for you.
  • Every call about meetings, records, tasks, slides and the stage names its tenant in the header Office-Tenant.
  • Every command carries a command_id that the client creates, a UUIDv7. A repeated command returns the stored result with duplicate set.
  • Every event has an id that grows by one inside a session, and a type in dotted form.
  • The contracts and their rules live with the part of the hub that provides them: the .proto files and the package comments below hub/. README.md says where to find them.

Give the participants the fingerprint

Section titled “Give the participants the fingerprint”

With the self-signed certificate, each participant checks it once with office hub add (see Set up once). Send them the address of the hub, the tenant and the SHA-256 fingerprint from the log of the hub (docker logs office-hub or the output of the hub). They compare it with the one that office hub add shows. They need no file. With a certificate from a public CA, they need nothing but the address. If a participant has no way to reach the hub when setting up, send the file tls.crt instead; it holds no secret. They store it as the ca-cert of a profile.

Create a tenant and register the participants

Section titled “Create a tenant and register the participants”

Create a tenant and name its first tenant admin, a user who is not a system admin. Each participant sends you their public key (see Join a meeting). You register it from your computer, then you or the tenant admin adds the user to the tenant. Registering a user and adding it to a tenant are two steps, so one user can work in several tenants:

Who may do what: a system admin creates, lists and removes users and tenants, names system admins and manages the members of any tenant. A tenant admin manages the members of the own tenant (admin member set and remove); a member lists them (admin member list). Everything else fails with permission_denied. A tenant that you are not a member of looks as if it did not exist (not_found), even to a system admin. Every call about meetings, records, tasks and slides names its tenant: the client sends the tenant of the hub profile, of --tenant or of OFFICE_TENANT.

office admin member set <tenant> <user> --role tenant-admin makes a member a tenant admin. office admin member remove <tenant> <user> ends a membership, and office admin member list <tenant> lists the members. office admin tenant list and office admin tenant remove <tenant> list and end tenants, office admin user list and office admin user remove <user> do the same for users. Removing ends the validity and keeps the record, so an ID is never used again. A tenant always keeps at least one tenant admin, and the hub at least one system admin.

office admin key add <user> <public key> adds a further key to a user. office admin key revoke <key-id> revokes a key. The last key of a user cannot be revoked.

Every user has a web portal in the browser. It shows what your key may see: your tenants, the sessions of a tenant in which you took part (a tenant admin sees all of them), the wiki of a tenant to its members (see Work on documents), the members of a tenant to its tenant admins, and the administration to system admins. There a system admin lists all users and keys, creates a user or adds a key with a form, and revokes a key after a confirmation, and sees the tenants and the system admins, read only. Tenants and memberships stay with the commands above:

The command prints a link. Open it in a browser within a few minutes: the link works once. The portal then stays open for one hour. After that, or if you see Portal link not valid or Session ended, run office portal link again. A system admin is no member of a tenant, so it opens the start page.
