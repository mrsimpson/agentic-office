3. Join a meeting

Set up once

Section titled “Set up once”

  1. Get the client (see Get the software). To speak, you also need a program that records the microphone: ffmpeg on macOS (brew install ffmpeg), parec on Linux (package pulseaudio-utils).

  2. Add the hub as a hub profile. A profile has a name, the address of the hub, your tenant and the certificate of the hub. Ask your admin for the address, the tenant and the fingerprint of the certificate (the hub logs it at its start):

    The command connects to the hub and shows the SHA-256 fingerprint of its certificate. Compare it with the fingerprint from your admin or from the log of the hub. Only if they are the same, answer y. The client then stores the certificate and writes the profile to config.yaml in your configuration folder ($CFG/client below). --default makes it the profile that the client uses when you name none. In a script, pass the fingerprint instead of answering: --fingerprint <sha256>. A hub with a certificate from a public certificate authority needs no stored certificate and no question.

  3. Create your key and send the public key to your admin:

  4. After the admin has registered you and added you to the tenant, check it: office whoami prints your participant ID.

Your private key stays in $CFG/client/key.pem. It never leaves your computer. $CFG is the folder of the client on your computer:

Work with several hubs

Section titled “Work with several hubs”

Add one profile per hub, with its own tenant:

Choose the hub for one command with --hub-profile, or for a shell with a variable:

A project can choose its hub too. Put the name into .office/config.yaml in the folder where you start the commands, and check the file in:

The order is: the default profile in your config.yaml, then the project file, then OFFICE_HUB_PROFILE, then --hub-profile; the last one wins. --hub, --tenant, --ca-cert and --key still override single values of the profile, for example --tenant other if you are a member of several tenants. office config show shows the active profile and where each value comes from. office hub remove lab removes a profile and its stored certificate. Profiles never hold a secret; the private key stays a file. A profile can name another key file with key: in config.yaml.

A profile is a whole hub. It sets the hub, the tenant and the certificate: a value that the profile leaves out is empty (no tenant, the system roots). The key is the exception: a profile without a key uses the key that is set without a profile. If a profile of the user file and one of the project file have the same name, they merge key by key.

Settings in files

Section titled “Settings in files”

You can keep settings in two YAML files instead of flags and variables: your user file, config.yaml in $CFG/client next to your key, for what holds for all your projects; and the project file, .office/config.yaml in the folder where you start the commands, for what belongs to the project, which you can check in. Each source overrides the one before it, key by key: the defaults, the user file, the project file, the environment variables, the flags.

  • The files never hold a secret. A key is the path of a key file, never the key itself.
  • The files are strict. A typo stops the command with exit code 2 and names the file, the line and the key, for example configuration file /work/.office/config.yaml, line 4: unknown key agent.wake.api-key.
  • A relative path in the project file is relative to the folder where you start the command; in the user file, relative to $CFG/client.
  • office config show prints what the client will use and where each value comes from.

office help config lists all flags, variables, keys and rules. The options of the agent runner are in the section agent of the same files (see Start an agent with a configuration file).

The speech models

Section titled “The speech models”

The client transcribes your speech on your own computer with Whisper. It chooses the speech model by the language you speak:

  • German: large-v3-turbo-german, a model fine-tuned for German (1.6 GB).
  • Other languages: large-v3-turbo (1.6 GB).
  • With --fast, or when your client cannot use a GPU: small (490 MB). It is fast on every computer, but makes more mistakes. The client says when it switches to small by itself. At the moment, only the client for Macs with Apple silicon uses the GPU.

Tell the client your language with --language, for example --language german or --language english (the default is German). The first join with the microphone downloads the chosen model once and checks it. To see which model the client would use, and to download it ahead of time, for example before your first meeting:

To use a certain model, name it: --model small, --model large-v3-turbo, or a path to a file. You can also set OFFICE_WHISPER_MODEL, a name or a file; --model and --fast win over it. Use a multilingual model, not a .en model: those only know English. --language auto lets Whisper detect the language.

The models are stored in ~/.local/share/agentic-office/models/ (or $XDG_DATA_HOME/agentic-office/models/). The client checks the SHA-256 of each download. If your network blocks the download, fetch the files elsewhere and set OFFICE_MODEL_URL to a mirror that holds them; office help models download names the files. make models fetches small and the VAD model for developers.

The client can also write the file for you. It reads the Markdown and text files of your project and finds names of people, organisations and places, and terms such as SyncEngine or DSGVO:

The first run downloads a model of about 540 MB. The run can take a few minutes for many documents. Then check .office/vocabulary.txt: delete what is wrong and move the most important terms to the top.

Speak in a meeting

Section titled “Speak in a meeting”

Use a headset: the client has no echo cancellation. Join with the name of the meeting, for example weekly:

  • Joining with the microphone means that you agree that your speech is transcribed and stored.
  • The terminal shows each of your sentences: final when Whisper has the text, sent when it is in the meeting log. Only text leaves your computer, never audio.
  • p pauses and resumes the microphone. o marks your last sentence as off the record: the others then see a placeholder instead of the text. q leaves.
  • On macOS, the system asks once whether your terminal may use the microphone.
  • A sentence ends after a short silence (500 ms). When you stay silent for longer after your last sentence (1.8 seconds), the ears end your turn: agents that wait for the end of a turn wake up then. While you are paused, nothing is transcribed and no turn ends.
  • When the network drops, the ears keep transcribing and send the sentences in order when the network is back. Sentences that are still waiting when you quit are lost; the client says how many.
  • --wav FILE plays a WAV file in real time instead of the microphone. This is how you try the ears without a headset.
  • Before you join, the client checks the models, the WAV file and the recorder. If something is missing, the join fails and you do not join. The client needs a recorder program that runs as your user; it tries parec, arecord, rec and, on macOS, ffmpeg. To use another one, set OFFICE_MIC_COMMAND.

office help ears lists every flag and variable of the ears.

Without a microphone, join with office meeting join weekly and write instead of speaking: office say "I agree". office meeting view shows your own sentences with their status.

Read the log and act from a shell

Section titled “Read the log and act from a shell”

office meeting join starts a small program in the background, the replicator. It copies the meeting into a local log, a file on your computer, and join prints its path. Each line of the file is one event as JSON. People and agents follow this file instead of asking the hub again and again:

  • The file is <runtime directory>/<session>/<participant>.jsonl. The runtime directory is $XDG_RUNTIME_DIR/agentic-office, else /tmp/agentic-office-<uid>, and private to you. Nobody can change a line: marking a sentence off the record adds a new line.
  • join starts the replicator detached and returns as soon as the file is open. This suits agents whose shell ends after each command. The replicator stops after the meeting ended or after you left. If the hub is not reachable, it keeps trying and reconnects by itself.
  • office meeting join weekly --foreground stays and prints the path. The replicator then stops when join ends, also when it is killed. Use it when you run the command as a background task.
  • Run office meeting join again to restart a replicator that was killed; it resumes the file. After a crash it cuts an incomplete last line and goes on after the last complete one.
  • The local logs stay until the runtime directory is cleaned, at logout for $XDG_RUNTIME_DIR. How long they should be kept is still open.
  • To read events from the hub instead of a file, for example to fill a gap or when you cannot follow a file: office meeting events --after 41 --limit 20.

Off the record. What is said stays said. You can mark your own sentence off the record (office utterance off-the-record 42, or --last; with the microphone, press o). Everyone who reads the session later gets a placeholder: the same event ID, "offTheRecord": true, no text. The stage hides it. Agents must not use such a sentence anywhere, and nobody should put it into minutes, decisions, notes or documents; the hub does not check this.

Other commands for the meeting: meeting pause and meeting resume, signal turn-end, signal silence-long and signal addressed for agents and scripts, hand raise.

Show the stage

Section titled “Show the stage”

The stage shows the meeting in two columns:

  • Left: the artifact in focus, large. The minutes are the first artifact: they are in focus until someone focuses another artifact. Until there are minutes, the stage asks you to bring in an agent that takes them (see Bring in an agent). When a session has more than one artifact, tabs appear above, with the minutes first. Below is a log of who created, changed or focused which artifact.
  • Right: the participants with their capture status (captured, paused, not captured), agents marked as agents, and a hand with a number for everyone who raised their hand, in the order they raised it. Under the name of an agent that runs with office agent run, the stage shows what it does: “working”, “working: fetch” with the kind or office tool it calls (never what it fetches or searches), “waiting”, or “answered only in its own chat” when its reply reached nobody. Below it is the transcript of the latest sentences.

The stage is dark or light, as your computer is set. One person creates a link, opens it in a browser and shares the window in your meeting tool (Zoom, Teams, Meet, Jitsi):

The link is read only and works for 24 hours (-stage-link-ttl of the hub), for this one session. Sentences that are off the record are not shown. A hand stays raised until its participant speaks, raises it again or leaves.

Work on documents

Section titled “Work on documents”

Anyone in the meeting, human or agent, can write a text document. A document is a Markdown file under documents/. You can show it on the stage:

A change names the version that you read (--base). If someone else changed the document in the meantime, the change fails with aborted and tells you the current version: read the document again and redo your change. Your name is recorded as the author of every change. Never put a sentence that is off the record into a document.

Front matter. Documents are the pages of the wiki of your team. A document may start with front matter that names the schema of documents. The hub then checks its fields and refuses a document with a wrong field, both through office document and with a push. Every field is optional, and no other field is allowed:

A document without front matter is fine too; its first heading is its title.

When a link of a document leads to no file, the hub writes the document anyway and gives a hint. office document create and office document change print each hint on stderr; --json puts them into the field hints:

A link to a document that waits for a release works: its stub is there.

A document that names a session (--session) waits for the release of the session, like the minutes (see Release what a session created).

Work on files in a local directory

Section titled “Work on files in a local directory”

The documents, notes, decisions, minutes, tasks and slides of your tenant are files in a Git repository on the hub. You can keep a copy of it in a directory on your computer and work on the files with your own tools: an editor, grep, or an agent with a shell. You need the git command line tool in your PATH.

How it fits together:

  • The main directory is a mirror of the branch main on the hub. The office moves it forward and never merges or commits there. A commit in it is refused.
  • You change files in a worktree: a second directory of the same clone, with its own branch.
  • You send your changes with plain git push. The hub checks every push and refuses a bad one.
  • A change of someone else (in a meeting, or by a push) reaches the main directory when you run office sync, or at once while office sync follow runs.
  • The copy holds artifacts only. The session logs are never in it.

Set up once. Use an empty or new directory. The command needs your hub profile and tenant (see Set up once) and your key:

The command writes into the Git configuration of this clone only. Your global Git configuration stays as it is. The clone gets:

  • you as the author: your display name and <participant ID>@office.invalid,
  • a helper that asks the hub for a fresh access token each time Git needs one, so no token is stored and none is in the address,
  • the certificate that your hub profile trusts,
  • a guard that refuses commits in the main directory.

Run office sync init again on a set-up directory to repair this configuration. It does not touch your files. It refuses any other directory that is not empty and changes nothing.

Update. Run this in the main directory, or name the directory:

If nothing is new, it says is up to date. The command moves main forward. If the hub rewrote the history of main, nothing of yours is on main, so the command moves main to the new state of the hub. Files that you changed and did not commit stay, unless the move would overwrite them. It stops and changes nothing when:

  • main has commits of its own: move them to a branch in a worktree and push that branch,
  • an incoming change would overwrite a file that you changed and did not commit: commit or move the file, then run the command again.

If a directory has the name of a command (init, follow or credential), write ./init instead of init. The command stops and asks for this form when both exist.

Follow. To keep the directory up to date while you work, leave this running in a terminal:

It updates once, then again after each change of an artifact, whether it came through a meeting or through a push. If the connection breaks, it connects again and updates. Stop it with Ctrl-C. --path limits which changes start an update, for example --path documents --path notes/plan.md. An update still brings everything.

Follow while you are in a meeting. You do not need office sync follow in a meeting. If you run office meeting join (or an agent calls the MCP tool meeting_join) in a set-up directory, or in a worktree of one, the clone is followed for as long as the meeting process runs: the replicator of join, or the MCP server. It updates once and then after each change. Nothing is printed on your terminal; the messages go to the log of the replicator (<participant>.replicator.log in the runtime directory) or to the log of the MCP server. In any other directory, join does nothing extra.

A problem with the clone never stops the meeting. It is written once to that log, in plain words, for example artifact sync: update of /home/ada/artifacts failed: ... the main directory has commits of its own. Fix it as described above. If a join finds a replicator that runs already, it reuses it and does not start a second follow.

Work in a worktree. Create a worktree and a branch next to the main directory, change files there, commit, and push to main of the hub:

The push moves main forward, and everyone who follows the tenant sees the change. The file documents/budget.md is now a document of the tenant, as if it had been made with office document create.

If you commit in the main directory, Git stops you and says where to work:

Plain Git and the certificate of the hub. office sync init writes the certificate that your hub profile trusts into the configuration of the clone (http.sslCAInfo). The variable GIT_SSL_CAINFO beats that setting. If it is set in your environment, plain git push and git fetch use the file of the variable and may say that the certificate is not trusted. The office commands ignore the variable for their own Git calls and print a warning when it is set and names another file. To fix plain Git, either:

  • unset the variable for this shell: unset GIT_SSL_CAINFO, or
  • point it at a bundle that holds the certificate of the hub as well as the authorities that you need, for example cat ca-bundle.crt hub-ca.pem > ~/my-bundle.pem, then export GIT_SSL_CAINFO=~/my-bundle.pem.

Do not turn off the check of certificates (GIT_SSL_NO_VERIFY, http.sslVerify=false).

When the hub refuses a push. The hub checks every push before it accepts it. A refused push changes nothing. The reasons are shown as remote: lines. Fix the cause and push again.

Reason Message (shortened) What to do
Wrong author commit c0028ab has the author Mallory <m@example.org>; every commit must have the author Ada Lovelace <ada@office.invalid> Set user.name and user.email as the message says, and amend the commits. A clone from office sync init has them right already.
Wrong file type notes.txt: only Markdown (.md) and YAML (.yaml, .yml) files are allowed Push only .md, .yaml and .yml files. No hidden files or folders (names that start with a dot), no links.
Invalid file documents/x.yaml: the schema "office.nothing.v1" is not known; the schemas are office.decision.v1, ... Fix the file. A file that names a schema must follow it. Any other .md or .yaml file only has to be valid text or YAML.
Too large documents/big.md is 1500000 bytes; a file may have at most 1048576 bytes Make the file smaller, or push fewer files. See the limits below.
Old base ! [rejected] HEAD -> main (fetch first) Someone changed main meanwhile. Run office sync, then git rebase main in your worktree, then push again.

Only the end result of a push counts for the file checks. A file that is broken in one commit and fixed in the next one is fine.

Hints. A push of a document with a link that leads nowhere is accepted, and the hub shows a hint for each such link. Links between the files of the same push work.

What is not allowed.

  • You can push to the branch main only. No other branch, no tag, no deletion, no forced push, no rewrite of the history.
  • Only Markdown and YAML files change. You may remove them.
  • The session logs are not in the clone and cannot be pushed. They can hold sentences that are off the record.
  • You need a key that is registered in the tenant. Another tenant looks as if it did not exist.

Limits. The operator of the hub sets them (see Start the hub with the binary). The defaults are 32 MiB for one push, 1 MiB for one file and 500 files changed in one push. Ask your operator if you need more.

Record decisions, notes and tasks

Section titled “Record decisions, notes and tasks”
  • The running minutes belong to the session. office meeting end stores the text of the last update as the minutes of the session. Read them later with office minutes show weekly or office minutes list.
  • After office meeting end, what the session created waits for its release; see the next section.
  • office session list lists the sessions in which you took part or that you imported, the newest first, with start, end and participants; a tenant admin sees every session of the tenant. The portal shows the same list on the page of the tenant (office portal link). Open a session there to read it: its minutes, decisions, tasks, notes and transcript, and its release with the staged artifacts. Sentences off the record do not appear.
  • A decision or a note is linked to a session only with --session, and only a participant of the session may name it. It then waits for the release of the session, like the minutes; see the next section. A decision or a note without a session is shared with the tenant at once.
  • A note is Markdown. Give it tags with --tag, once per tag. The hub stores it as a Markdown file notes/NNNNNN.md: the front matter names the author, whether the author is a human or an agent, the time, the session and the tags, and the body is the text.
  • For now a task is a local draft in the hub. Its reference, for example local:42, is opaque: keep it and pass it back. The statuses are open, in_progress, done and cancelled. Any participant may read and change every task. With --session "" or --assignee "" you remove the session or the assignee.
  • The list commands show the oldest first, at most 100 at a time (--limit, at most 1000). task list prints the token of the next page on stderr; pass it as --page-token.

Release what a session created

Section titled “Release what a session created”

Every member of the tenant reads the artifact repository, and nothing can be taken out of it again. So what a session creates waits in a staging area of the session until it is released. Only the people and agents who took part read it there.

  • Who releases. Every human who took part may release or object, also after leaving. An agent never does; the hub refuses it. If no human took part, for example a meeting of agents or an import that only agents worked on, the hub releases the session at its end.
  • The grace period. Otherwise the hub releases the session 24 hours after its end. The operator sets another length for the whole hub with office-hub -release-grace-period 2h.
  • During the grace period you can still mark your own sentence off the record. That mark reaches no local log and no agent any more: correct the staged files yourself, ask their authors, or object with office session hold. An objection holds the session until a human releases it.
  • The release moves everything the session staged into the artifact repository in one commit, with you (or the hub) as the author, and the authors of the artifacts as co-authors.
  • A path that is taken. The release replaces only the stub of a staged artifact, or writes where no file is. If someone pushed their own file at that path, for example while the hub was down, the release keeps the pushed file and releases everything else. The staged artifact is then not released: it stays in the staging area, and the people who took part still read it. The page of the session in the portal shows it as “not released: the path is taken”. To keep it, read it and create it again at a new path with the command of its type, for example office document get documents/plan.md and then office document create documents/plan-2.md --file plan.md.
  • Quotes off the record. Before every release, the hub searches the staged files for sentences that are off the record, word for word (sentences of at least three words; case and spaces do not count). If it finds one, it refuses the release. office session release then prints each place (file, line and the event of the sentence, never the sentence) and a token, and exits with 1. Correct the files and release again, or release anyway with --accept-quotes <token>. The hub searches again and releases only if it finds exactly the same quotes; if a staged file changed in between, you get new places and a new token. The hub changes no content.
  • The grace period ends with quotes. Then the hub does not release the session but holds it, as if someone had objected. A human who took part releases it with the token. A session without humans is released at its end all the same.
  • In the portal, the page of a session shows the release status, when the hub releases it, and the staged artifacts to everyone who took part and to the tenant admins. A human who took part gets a button to release and, while the session waits, one to object. If the hub refuses a release because of quotes, the page lists the places and a button “Release anyway”. Other members see a session only after its release: the released artifacts, who released them and their authors.
  • After the end, a session takes only the release, the objection, notes about artifacts and, until the release, marks off the record.

Staged minutes, decisions, notes, documents and slides. Until the release, every participant of the session may correct or remove them. Name the session of the artifact with --session:

  • Only the participants of the session and the tenant admins read a staged record. Every other member sees only its number and that it waits for a release; the artifact repository and every clone hold the same stub instead of the record.
  • A removed record is gone for good: its number is not used again, and only a new record brings its content back.
  • After the release a record never changes. Record a new one that refers to it. A released document changes with document change like any other document, and the change is shared at once, whatever session it names. A released deck does not change; render a new one.
  • A record, a document or a deck that names a session that is already released is shared with the tenant at once.
  • The stage of a session shows the staged artifacts of that session. A staged artifact of another session shows as its stub.

Bring in an old conversation

Section titled “Bring in an old conversation”

You can import a conversation from another tool, for example a chat export or a meeting transcript, as a session of its own. Convert it to the import format first (office help import-format shows it), then:

The session is marked as imported: its log starts with the source and the importer, the stage says so and shows “Imported” instead of “Live”, and the imported speakers are marked.
